## Plan: give the LLM broader editor access

The governing design is: **the LLM chooses an action and its target; Worrek validates that choice against the live document and executes it through a typed adapter.** The open browser editor is the source of truth for unsaved changes. This follows the editor vendor’s [agent integration guide](https://www.docx-editor.dev/docs/2.x/build-a-docx-agent) and its [atomic batching and stale-document guidance](https://www.docx-editor.dev/docs/2.x/editor-api/batching-and-errors).

Worrek already has the core path: live snapshot → `editDocument` proposal → validation → user approval → browser automation → result. The work is to expand that path in controlled pieces ([chatEditor.ts](/home/selor/linux/my-projects/worrek/frontend/src/_lib/chatEditor.ts:67), [contracts.ts](/home/selor/linux/my-projects/worrek/backend/src/lib/chat/contracts.ts:91), [chatPanel.tsx](/home/selor/linux/my-projects/worrek/frontend/src/_components/documentEditor/chatPanel.tsx:246)).

### Boundaries to design explicitly

- **Execution:** The browser adapter resolves IDs to current editor handles immediately before applying an approved action, checks the revision and expected content, then uses the editor’s transaction path. A stale result triggers a fresh read and a new proposal. [Automation API](https://www.docx-editor.dev/docs/2.x/api/core/automation)
- **Scope:** Main-body paragraphs are currently represented; headers, footers, notes, tables, and controls need explicit story and object identities. The API treats them as separate scopes. [Page layout and stories](https://www.docx-editor.dev/docs/2.x/editor-api/page-layout-and-stories)
- **Special capabilities:** Images require validated image bytes. Field results require measured pagination. Browser comments and tracked changes require the appropriate Pro review setup and an author. These should enter the rollout only after their prerequisites are confirmed. [Pictures](https://www.docx-editor.dev/docs/2.x/editor-api/pictures), [fields](https://www.docx-editor.dev/docs/2.x/editor-api/fields), [review](https://www.docx-editor.dev/docs/2.x/editor-api/revisions)
- **Frontend boundary:** Keep the live editor adapter and approval interactions in a Client Component. Keep model calls, credentials, and server validation on the backend; Next.js pages and layouts can remain Server Components. [Next.js component guide](https://nextjs.org/docs/app/getting-started/server-and-client-components), [`use client` reference](https://nextjs.org/docs/app/api-reference/directives/use-client)

**Recommended first milestone:** complete phases 1 and 2, then prove the whole flow with “make this phrase blue and 14 pt” and “center this paragraph with 6 pt spacing.” That validates the contract and execution pattern before adding structural actions.
